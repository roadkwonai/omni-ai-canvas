# 디렉터 스튜디오 · 연출 참고자료 반영 계획

작성일 2026-11-24 · 상태 **1~3단계 구현, 4단계 보류** (예제 방식 C) · 관련 기준 C3·C4·C6·C7

디렉터 스튜디오에서 샷·구도·시선·카메라 무브먼트를 **움직이는 예제로 보고 고르며**, 고른 기법이 이름이 아닌 **구체적인 촬영 지시**로 생성 요청에 들어가게 한다.

## 1. 지금의 문제

| 문제 | 근거 |
| --- | --- |
| 기법 이름만 전송한다 | `directorNote`에 `카메라 이동: 돌리 인`처럼 저장하고 `lib/run-input.ts`가 그대로 보낸다. 노션 구도 자료도 이름만 쓰면 결과가 부정확하므로 인물 위치, 빈 공간, 선의 방향을 적으라고 설명한다. |
| 예제가 기법을 보여주지 못한다 | 카메라 이동 7개가 같은 정지 이미지다. 구도 4개에 회색 여백이 있고 익스트림 클로즈업·오버숄더·인서트의 그림이 뜻과 다르다. |
| 항목이 적다 | 앵글은 4개짜리 선택 목록이고 화면 배치·시선·시간 표현 항목이 없다. |
| 정지 이미지 요청에도 움직임이 들어간다 | 이미지·영상을 구분하지 않고 카메라 이동과 편집 리듬을 함께 보낸다. |
| 긴 목록에서 찾기 어렵다 | 검색이 없고 선택 요약은 스크롤 맨 아래에 있다. |

같은 노션·CineGuide 자료는 [이전 검토](directing-sources.md)에서 연출 도구(`lib/staging.ts`)의 텍스트 설계에 반영했다. 이번 계획은 노드별 디렉터 스튜디오에 예제와 전송 지시를 붙이는 작업이다.

## 3. 예제 자산 · 결정이 필요한 부분

| 방식 | 내용 | 장점 | 한계 |
| --- | --- | --- | --- |
| **A. 내 컴퓨터 보관함** | CineGuide 파일을 내려받아 `.scene-room/research/cineguide/`에 두고 앱에서만 재생한다. | 요청한 그대로 쓴다. 예제 품질이 높다. | 권리자의 이용 허락을 확인하지 못했다. 앱이나 저장소를 공유할 때 함께 넘길 수 없다. 앱이 공개되면 허락을 받거나 B로 바꿔야 한다. |
| **B. 자체 제작** | 정지 예제는 구독형 `image_gen`, 움직임은 로컬 Blender 반복 영상으로 만들어 `public/director/`에 둔다. | 배포할 수 있고 모든 카드의 인물·장소가 같다. | 제작 시간이 들고 실사 느낌이 덜할 수 있다. |
| **C. 함께 쓰기 (권장)** | 기본 예제는 B로 채우고, A의 파일이 있으면 그 영상을 보여준다. | 요청을 들어주면서 공유할 때도 빈 카드가 없다. | 두 경로를 관리한다. |

A·C의 처리 기준은 다음과 같다.

- `public/`에 넣지 않는다. `.scene-room`은 이미 `.gitignore`와 `next.config.ts`의 빌드 추적에서 제외된다. 기존 지침 원문 보관(`app/api/guidance/route.ts`)과 같은 방식이다.
- 파일마다 원본 주소, 받은 날짜, SHA-256을 목록(`manifest.json`)에 적고 카드에 "예시 · CineGuide (Sputlab × AInspire)"와 원본 링크를 표시한다.
- 원본은 4K가 섞여 크다. 로컬에서 640px, 무음, H.264로 줄인다. 원본 37개에서 예제 41개를 만들었고 합계 4.7MB다.
- 하이·로우 앵글, 정면·측면·뒷모습, 시선 영상은 한 파일에 여러 기법이 들어 있어 구간을 나눈다.
- 로그인이 필요한 수강생 자료는 가져오지 않는다.

### 카드 한 장의 정보

```
┌──────────────────────┐
│  5초 반복 영상        │  마우스를 올리거나 포커스하면 재생
│                      │  움직임 줄이기 설정이면 첫 화면만 표시
├──────────────────────┤
│ 돌리 인   Dolly In    │
│ 인물에게 다가가며     │  용도 한 줄
│ 긴장을 높입니다       │
│ 예시 · CineGuide ↗    │  A의 자산일 때만
└──────────────────────┘
```

### 생성 요청에 들어가는 지시

저장값은 지금처럼 이름이다. 요청을 만들 때 이름을 지시로 펼친다. 2,000자 제한과 기존 저장값이 유지되고, 이미 저장한 노드도 개선된 지시를 받는다.

```
카메라 이동: 돌리 인
  → 카메라가 초점 거리를 고정한 채 피사체를 향해 천천히 직진한다.
    배경의 원근이 함께 변한다. 유지: 인물의 위치·의상·얼굴.
    피할 것: 디지털 줌, 컷, 배경 왜곡.
```

- 프리셋에 `id`(예제), `en`(영문 이름), `spec`(160자 이내 한국어 지시와 피할 것)을 둔다. 요청이 길어지지 않도록 영문 지시 전체는 보내지 않고 영문 이름만 덧붙인다.
- 이미지 요청에는 카메라 이동, 시간 표현, 편집 리듬을 보내지 않는다. 디렉터 스튜디오가 저장한 형식(`촬영 및 시각 연출`로 시작)에만 적용하고 자유 문장은 바꾸지 않는다.
- 편집 연결은 단일 클립 요청에 보내지 않는다. 클립 하나를 컷 없이 만들도록 요청하는 자료의 원칙과 맞춘다.
- 직접 입력한 값은 펼치지 않고 그대로 보낸다.
- "생성 요청에 적용할 내용"에는 실제로 전송할 펼친 문장을 보여준다.

## 9. 초점 거리 확대 화질 보완 · 구현 완료 (2026-11-24)

### 원인

예제 `focal-platform.webp`는 1672×941 한 장이고, 화면은 이 사진을 CSS로 확대한다. 초점 거리가 길수록 쓰는 원본 픽셀이 줄어든다. 창을 키우면서 예제 폭이 482px에서 796px로 커져 흐림이 더 잘 보인다.

| 초점 거리 | 사용하는 원본 폭 | 796px 화면 확대율 | 고해상도(2배) 화면 |
| --- | --- | --- | --- |
| 35mm | 860px | 0.93배 | 1.85배 |
| 50mm | 602px | 1.32배 | 2.64배 |
| 85mm | 354px | 2.25배 | 4.50배 |
| 135mm | 223px | 3.57배 | 7.14배 |

### 시험

중앙부를 잘라 구독형 `image_gen`으로 같은 구도의 세부를 복원하고, 원본과 블록별 위치를 대조했다. 값은 폭 836px 기준의 어긋남이다.

| 방식 | 중앙값 | 90% | 최대 | 판단 |
| --- | --- | --- | --- | --- |
| 원본에서 48mm 복원 | 0px | 1.0px | 1.4px | 사용 가능 |
| 원본에서 135mm 바로 복원 | 1.0px | 8.1px | 27.6px | 이음새가 보여 제외 |
| 선명해진 48mm에서 115mm 복원 | 0px | 1.0px | 7.3px | 사용 가능, 가장자리 보정 필요 |

### 방법

1. 18mm 원본 위에 48mm와 115mm의 세부 이미지를 실제 화각 위치에 겹친다. 모두 같은 비율로 함께 확대하므로 값을 바꿔도 그림이 튀지 않는다. 115mm로 만드는 이유는 135mm에서 가장자리의 흐린 경계가 화면 밖에 놓이기 때문이다.
2. 겹치는 가장자리 12%를 부드럽게 섞고 평균 밝기와 색을 원본에 맞춘다. 시험본의 85mm에서 외투에 옅은 가로 경계가 남아 이 보정이 필요하다.
3. 최대 확대율은 796px 화면에서 3.57배 → 1.24배, 고해상도 화면에서 7.14배 → 2.5배가 된다. 추가 용량은 약 0.6MB이며 30mm를 넘을 때 읽는다.
4. 위치 대조를 테스트로 남겨 이미지를 바꿀 때 어긋남을 잡는다. 초점 거리 버튼의 글자 정렬도 함께 고친다.

| 다른 방법 | 쓰지 않는 이유 |
| --- | --- |
| 기존 로컬 업스케일 | 보간과 선명화라서 없는 세부를 만들지 못한다. |
| 공급사 업스케일 | 크레딧을 쓴다. |
| 초점 거리별 사진 따로 생성 | 값을 움직일 때 인물과 배경 위치가 튄다. |
| Blender 렌더 | 선명하고 정확하지만 실사 예제와 느낌이 다르다. |

## 10. 카메라·렌즈·조리개 효과 샘플 · 구현 완료 (2026-11-24)

### 검토 결과

카메라와 렌즈의 실물 사진으로는 결과 화면의 차이를 알 수 없다. 고르는 기준은 심도, 입자, 빛 번짐, 배경 크기이므로 **같은 장면을 그 장비로 찍은 결과**를 보여주는 편이 맞다. 생성 요청도 같은 문제가 있다. 카메라·렌즈·조리개는 구도나 카메라 이동과 달리 펼칠 지시(`spec`)가 없어 이름만 전송된다.

같은 인물과 승강장의 저녁 장면 12칸을 구독형 `image_gen`으로 시험했다. 대형 센서, 아나모픽, 빈티지, f/1.4와 f/11은 한눈에 구별된다. 디지털 시네마·구면 단렌즈·f/4는 서로 비슷하고 필름 입자와 망원의 압축감은 작은 칸에서 약하다. 시트 한 장으로 나누지 않고 **한 장씩 크게** 만들어야 한다.

### 방법

1. 저녁 조명의 기준 사진 한 장(상반신)을 정하고, 이 사진을 편집해 카드별 결과를 만든다. 인물·자세·구도를 유지하고 광학 효과만 바꾼다.
2. 카드에 결과 사진을 보여주고, 누르고 있거나 **기준과 비교**를 켜면 기준 사진을 보여준다. 장비 실물 사진은 카드에서 뺀다.
3. 조리개를 선택 목록에서 카드로 바꿔 심도 차이를 보여준다. 값 이름은 그대로 두어 저장된 노드를 연다.
4. 카메라·렌즈·조리개에 화면에 나타날 효과를 적은 지시를 붙인다. 예: 아나모픽 렌즈 → "광원에 가로로 긴 빛줄기와 세로로 긴 타원 보케를 만든다. 피할 것: 둥근 보케, 과한 왜곡."
5. 망원 줌과 짧은 초점 거리, 어깨 장착과 고정·돌리처럼 어긋나는 선택을 안내한다.

| 구분 | 지금 | 추가 제안 |
| --- | --- | --- |
| 카메라 | 디지털 시네마, 대형 센서 시네마, 어깨 장착 다큐멘터리, 아날로그 필름 | 16mm 필름, 스마트폰, 캠코더, CCTV |
| 렌즈 | 구면 단렌즈, 아나모픽, 빈티지, 망원 줌 | 매크로, 초광각·어안, 소프트 디퓨전 필터, 틸트 시프트 |
| 조리개 | f/1.4, f/2, f/2.8, f/4, f/5.6, f/8, f/11 | 없음 |

결과 사진은 23장이다. 비슷해 보이는 조합은 다시 만들고, 이름을 가린 채 구별되는지 확인한다. 어깨 장착 다큐멘터리는 움직임이 핵심이라 정지 사진과 함께 기존 핸드헬드 영상을 보여준다.

### 확인할 점

샘플은 효과를 설명하는 예시다. 실제 장비의 측정 결과가 아니며 선택한 모델이 같은 효과를 내는지는 생성해 봐야 안다. 화면에도 "효과 예시"라고 적는다.

### 9·10절 구현 결과

- 초점 거리 세부 이미지 두 장(`focal-48.webp`, `focal-115.webp`, 합계 0.6MB)을 겹쳤다. 24·50·54·85·100·135mm 화면에서 이음새가 보이지 않았다. 위치 검사는 바로 아래에 깔리는 이미지와 비교해 폭 418px 기준 90%가 1.5px 이내다.
- 결과 사진 23장과 기준 사진 한 장을 구독형 `image_gen`으로 만들었다. 어깨 장착 다큐멘터리, f/4, f/5.6은 차이가 약해 한 번 다시 만들었다. 시험을 포함해 이미지 생성 32회를 썼고 유료 API와 크레딧은 쓰지 않았다.
- 어깨 장착 다큐멘터리는 처음에 6도 기울기와 번짐이 강한 사진과 핸드헬드 영상을 붙였으나 기법과 달라 바꿨다. 어깨 장착은 손에만 든 촬영보다 안정적이고 호흡과 걸음의 작은 움직임이 남는 중간 성격이다([장비 안내](https://www.smallrig.com/blog/shoulder-rig-vs-stabilizer-comparison-guide.html), [용어 설명](https://morphic.com/ai-glossary/shoulder-mount)). 수평을 지킨 관찰 사진 한 장에 `scripts/director-shoulder-clip.mjs`로 작은 움직임을 더한 같은 장면의 영상을 둔다. 카드 사진과 재생 영상이 같은 장면인지는 `tests/node-director-optics.test.ts`가 검사한다.
- f/8과 f/11의 배경 선명도는 비슷하다. f/11은 광원의 별 모양과 어두워진 밝기로 구별한다.
- 비교 화면은 누르고 있는 방식 대신 카드마다 왼쪽 기준, 오른쪽 결과로 나눈다. 화면 범위가 달라지는 다섯 항목(어깨 장착 다큐멘터리, CCTV, 망원 줌, 매크로, 어안)은 결과만 보여준다.
- 원본은 `.scene-room/research/director-trials/`에 보관한다.
